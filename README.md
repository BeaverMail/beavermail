# BeaverMail client

Desktop mail client written in Rust with [egui](https://github.com/emilk/egui) (eframe).
Licensed under AGPL-3.0-only (see [LICENSE](LICENSE)).

## Layout

- `crates/core`: domain model and the `MailSource` trait. No GUI or network dependencies.
- `crates/store`: the local mail index (SQLite, full-text search); it holds no message bodies.
- `crates/vault`: the message files, their encryption and key slots.
- `crates/imap`: IMAP backend (`ImapSource`), which keeps the archive in sync.
- `crates/smtp`: sending (`SmtpSender`).
- `crates/accounts`: `accounts.toml` and the system credential store.
- `crates/app`: the egui desktop shell (binary `beavermail`).

## Status

Several IMAP accounts with folders, message list and reader. Messages can be marked read or unread,
archived, moved to Trash and erased from Trash (keys: Up/Down, E, Delete, U). New messages, replies,
reply all and forwards are sent over SMTP (keys: C, R, A, F), with a copy kept in Sent. Accounts can
be edited from the sidebar. Messages open as plain text by default, or as simplified HTML (Settings, or per message and per
sender); images and styling are never loaded and tracking parameters are removed from links.
Mail is kept locally: the window opens from a SQLite index, and each downloaded message is an
file under the data directory, encrypted by default (XChaCha20-Poly1305). Settings choose between a key
kept by the system, a passphrase, or no encryption.
New mail shows up by itself: the Inbox is watched with IDLE (or polled every few minutes on servers without it),
and mail, flags, deletions and older history sync in the background, and the messages themselves
download in the background (per account: everything, last 12 months, last 30 days, or only opened
messages), with progress and a pause button in the status bar. The index (SQLCipher) follows
the same setting and is encrypted with a key derived from the message key. The search box looks in senders,
subjects and message text (`from:`, `subject:`, `is:unread`, `has:attachment` narrow it).

The list shows the sender's domain next to the name, because a name is free text ("Your Bank" can come from anyone). A name that claims another address or site, or a domain written with look-alike characters, is flagged in red in the list and in the reader.

In the reader, the checks your own mail server already made (SPF, DKIM and DMARC, from its `Authentication-Results` header) say whether the sender's domain is real: verified, or flagged in red when the message does not come from the domain it claims or the server's spam filter marked it. Only the header written by your server counts; one put there by the sender is ignored. A flagged message never loads remote content on its own, whatever permission its sender had.

The reader adds checks only this computer can make, from whom you write to (the recipients of your Sent folder) and what the message contains: your own name or the name of someone you know on a stranger's address, a brand in the name (PayPal, your bank, an organisation you deal with) sent from a domain that is not the brand's, a domain one character off one you write to (`acme-c0rp.com`), replies diverted to a public mailbox, an address generated by a machine, links whose text names another site or that open a bare IP address or a look-alike domain, long hidden text, and attachments that are programs, web pages, macro documents or (from strangers) archives. Most of these need only the header fields, which the sync keeps for the Inbox, so they work before the message is downloaded. Dates are shown in this computer's time zone.

Mail from people you know is never touched: someone you have written to, anyone at an organisation you write to (public mailbox providers such as Gmail do not count), a reply to a message you sent. Mail from a new sender reaches the Inbox unless one of the checks above fails, its text matches a campaign you already have as spam (a fingerprint of its phrases, compared across sender domains), or a classifier learnt from your own mail rates it 90% spam or more (a logistic regression trained online with FTRL over words and word pairs; it is rebuilt from the messages you called spam or not spam, which are kept as examples in the archive, the Spam folder, whose headers are synced for this, and the mail of known senders, and stays off until it has 20 examples of each kind). Your server's verdict counts too: `X-Spam-Bar`, and SPF failures in its SpamAssassin report. Such mail is held under the Inbox as "Suspicious" (on this computer only, nothing moves on the server), and so is mail your server says is forged. The reader offers the one correction that makes sense: "Not spam" on held mail; "Spam" on mail from a new sender, which moves it (and the sender's other Inbox mail) to the server's Spam folder; and "Not spam" in the Spam folder, which moves the message back to the Inbox. "Move all to Spam" does the same for everything held. The list shows the failed check in place of the preview, so spam is judged without opening it; `!` marks the selected message as spam, and opening held mail or spam does not mark it as read. A mark covers the whole organisation (or the address at a public provider); Settings lists the marks, can forget them, and turns holding off. Each message is checked once: its verdict is kept in the archive, so opening the Inbox or a sync checks only new mail; "Check all mail for spam" in the Inbox's menu (right click) checks every message again. "Empty Spam…" in the Spam folder's menu erases its messages from the server after asking; they stay as examples for the checks to learn from. To see what the checks do to each Inbox without the app, run `cargo run -p beavermail -- --screen-dry-run`: it syncs the folder list, Sent and Inbox read-only, then prints where each message goes and why, and how much the fingerprints and the classifier have to learn from. Nothing is moved and no mark is saved.

Attachments are listed in the reader and can be opened, or saved one by one or several together
through a file dialog (programs and macro documents ask before opening). Files can be attached to new
messages with the Attach button or by dragging them in (drag and drop works on Windows, macOS and X11;
on Wayland the toolkit does not support it yet, so start the app with `WAYLAND_DISPLAY=` to use X11). Forwards carry the original attachments.

Messages open in tabs: a click shows a message in the reading pane; a double click, a middle click, Ctrl+click or Enter opens it in a tab of its own, as wide as the window, which stays when another folder or account is shown. The tab bar appears across the top with the first tab open; its first tab, Mail, goes back to the folders and list. Ctrl+W closes a tab, Ctrl+Tab and Ctrl+Shift+Tab move between them and Mail.

What you write is kept as a draft on this computer (saved a moment after you stop typing, inside the
encrypted vault, with its attachments); open the Drafts folder to pick it up again. A copy of the draft is also
kept in the server's Drafts folder (after a longer pause, and when you close the window), so other devices see it;
opening a draft made elsewhere is not supported yet. Messages are written in Markdown (a small toolbar and a preview; Settings turns it off) and sent as plain text plus a simple HTML version, with no images or tracking. Besides plain text and simplified HTML, a message can be read as "Original HTML": layout and colours as the sender designed them, drawn by Blitz (no browser, no scripts); nothing is fetched from a server until you press "Load for this message" (or "Always for this sender", which Settings lists and can revoke), so by default nothing can track you. When loaded: GET only, no cookies or referrer, no servers on the local network, size and count limits. No end-to-end message encryption yet.

## Running

```sh
cargo run -p beavermail
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```
